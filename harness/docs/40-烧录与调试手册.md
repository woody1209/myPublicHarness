# 40 · 烧录与调试手册

## 调试器连接（LAUNCHXL-F280039C）

- 板载 **XDS110**，FMware 3.0.0.43；走 **cJTAG (1149.7) 2-pin advanced**。
- ccxml 必须使用官方 LaunchPad 版本：
  `projects/<proj>/targetConfigs/TMS320F280039C_LaunchPad.ccxml`
  其 `<property Type="choicelist" Value="4" id="SWD Mode Settings"/>` 即 2-pin cJTAG。
- 连接前提：USB Type-C 上电、**JP1/JP2 对应 Shunts 应安装**（否则 XDS110 与 MCU 两侧电源隔离，
  会出现"探针在线但连不上目标"）。

## 常用命令（唯一入口）


  `syntax error: unexpected end of file`（2026-10-17 复现并修复）。
- 烧录门禁已在上板实跑通过（2026-10-17）：`probe`（只读枚举，XDS110 SN CL391078）→

## C28x 字地址模型（读 map / 读寄存器 / 写 DSS 脚本前必读）

C28x 工具链里**所有地址都是 16 位"字"地址**——编译器常量、链接器 `.cmd` 的 origin、map 文件的
地址**与 size**、反汇编地址、DSS `memory.readWord()`、`PC`/`XARn`，无一例外：

| 事实 | 数值 |
|---|---|
| `sizeof(uint32_t)` | 2 字 = 4 真实字节 |
| map 文件 size 列 | 字（例：`led_hw_channels`（16 字节）map size = `0x08` = 8 字） |
| `*+XARn[N]` 位移 | N 个字（`MOVL` 32 位写也按字寻址） |
| `memory.readWord(0, a)` | 读 **一个** 16 位字；32 位寄存器必须读两个字再拼接 |
| C 字节 | 16 位（`CHAR_BIT == 16`），C 源码里的"字节"与"字"同义 |

证据链（2026-10-17 五方交叉验证，详见 ADR 0002）：链接脚本 `FLASH_BANK0_SEC4 origin = 0x84000`
↔ map `.const@0x84000`；`led_hw_channels`（`{u32;u32;}[2]` = 16 字节）map size `0x08` = 8 字；
反汇编 `led_hw_apply` 载入 `MOVL XAR4,#0x084432` 与 map 地址一致；DSS `readWord(0, 0x84432)`
依次读到 `0x0014 / 0x0800 / 0x0016 / 0x0C00`——即 flash 常量表
`pin=20, cfg=0x00080800, pin=22, cfg=0x00080C00` 的正确低半字。

> **踩坑教训**：曾按"真实字节"模型推导出"driverlib GPIO 寻址存在 2× bug"的错误结论，
> 差点绕开 driverlib 直接写寄存器。按字地址模型重新对账后 driverlib 寻址**完全正确**
> （见下节），固件与 driverlib 都无需改动。详见 ADR 0002。

## GPIO 寄存器真实布局（字地址；2026-10-17 实证）

`GpioCtrlRegs` @ **0x7C00**（GPIOCTRL，len 0x200 字）、`GpioDataRegs` @ **0x7F00**（GPIODATA，
len 0x40 字）、`GpioDataReadRegs` @ **0x7F80**（GPIODATAREAD）。bank（A=GPIO0-31 /
B=GPIO32-63）在控制块中间距 **0x40 字**、数据块中间距 **8 字**：

| 寄存器 | 字地址 | 宽 | 说明 |
|---|---|---|---|
| GPAMUX1 / GPAMUX2 | 0x7C06 / 0x7C08 | 32 位 | 引脚功能复用（GPIO16-31 的字段在 MUX2） |
| GPADIR | 0x7C0A | 32 位 | 方向（1=输出） |
| GPAPUD | 0x7C0C | 32 位 | 上拉禁用的位：**1=禁止上拉**；复位默认全 1（C2000 上拉默认关闭） |
| GPAINV / GPAODR | 0x7C10 / 0x7C12 | 32 位 | 输入反相 / 开漏 |
| GPAGMUX1 / GPAGMUX2 | 0x7C20 / 0x7C22 | 32 位 | 外设组复用（与 MUX 位组合选功能） |
| GPBCTRL / GPBDIR | 0x7C40 / 0x7C4A | 32 位 | bank B 同布局（+0x40 字） |
| **GPADAT** | **0x7F00** | 32 位 | 数据寄存器：字 0x7F00=GPIO0-15，字 0x7F01=GPIO16-31（**LED4=bit4、LED5=bit6**） |
| GPASET / GPACLEAR / GPATOGGLE | 0x7F02 / 0x7F04 / 0x7F06 | 32 位 | 写 1 置位/清零/翻转；**只写**（读回恒定） |
| GPBDAT | 0x7F08 | 32 位 | bank B 数据（GPIO32-63，含 JTAG 引脚 35-38） |
| **GPADAT_R** | **0x7F80** | 32 位 | 引脚实际电平读回（字 0x7F81 = GPIO16-31） |

实证终态（diag15，2026-10-17 08:02）：GPAMUX2=`0x0500`（GPIO28/29 复用为 SCIA RX/TX）、
GPADIR=`0x2050`（GPIO20/22/29 为输出）、GPAPUD=`0xFFFF`（全部禁止上拉）、
GPADAT 高字=`0x3144` 且 GPADAT_R 高字=`0x0040`——**GPIO20=0（LED4 亮）、GPIO22=1（LED5 灭）**，
与固件设计完全一致。driverlib `GPIO_writePin` 编译产物 `MOVL *+XAR4[2],ACC`（SET@0x7F02）/
`MOVL *+XAR4[4],ACC`（CLEAR@0x7F04）与设备头结构体字偏移逐一相等，**driverlib 寻址无罪**。

driverlib C 常量对账（全部在字单位下相等）：`GPIO_CTRL_REGS_STEP=(0x40-0)/2=32`、
`GPIO_DATA_REGS_STEP=(0x8-0)/2=4`、`GPIO_GPxDIR_INDEX=0xA/2=5`、`GPIO_GPxSET_INDEX=1`、
`GPIO_GPxCLEAR_INDEX=2`、`GPIO_MUX_TO_GMUX=0x20-0x6=0x1A`。

## 外设时钟门控与 CPUTIMER 时基（2026-10-17 实证；新工程必读）

CPUSYS 基址 **0x5D300**（字地址；driverlib 直接把 `SYSCTL_O_*` 偏移加在字基址上）：

| 寄存器 | 字地址 | 关键位 |
|---|---|---|
| PCLKCR0 | 0x5D322 | bit3 = CPUTIMER0 时钟（应用运行时实测 `0x1000039`） |
| PCLKCR7 | 0x5D330 | bit0 = SCIA 时钟 |
| RESC | 0x5D380 | bit0 POR / bit1 XRSn / bit2 WDRSn / bit31 DCON（仿真器在线） |

- **复位后外设时钟默认关断**，此时对该外设帧的读写**不报错**，但**每一次写都被静默丢弃**。
  SCIA 表现：`CTL1` 恒 0x0000（应为 0x000B RXENA|TXENA|SWRESET）、`LBAUD` 恒 0（应为 0x1F），
  串口一个字节都不出——A/B 实验（diag17）证实：写同一寄存器，置位 PCLKCR7 前后写效果天差地别。
  结论：**用哪个外设，先 `SysCtl_enablePeripheral(SYSCTL_PERIPH_CLK_x)`**。TI 自带
  `InitSysCtrl()`（`f28003x_sysctrl.c:186`）就置了 SCI_A 位；纯 driverlib 移植漏掉它 = 日志全哑。
  HIL 的 H3 现在直接读 0x5D330 做守卫（`H3-sciclk`）。
- **CPUTIMER0 以 SYSCLK 递减**（TPR=0 时 120MHz，不是 LSPCLK=30MHz）。无停机探针实测：
  PRD=30000 → LED 平均翻转 51.4ms（= 200 拍 × 257µs），据此否掉了"按 SYSCLK/4 算周期"的误判。
  周期就是 `BOARD_SYSCLK_FREQ_HZ / tick_hz`。
- **TIF 是一个标志位，不是计数器**：核心 halt 期间定时器即使继续跑（TCR ICEM 已设为
  `RUNFREE`，0x0800），多个溢出在恢复后也只被轮询主循环累加**一次**。所以任何"暂停—读—再跑"
  的采样都会把节拍拉长（实测 200ms 步长报成 426ms）。**时序必须用无停机 peek 测**
  （`hil_test.js` H5 已改为运行态直接读 GPADAT_R 双字）。

## 固件启动顺序（C28x 硬约束，2026-10-17 实证；新工程必须照抄）

`main.c` 的入口顺序不是风格选择，是踩过坑的硬约束。C28x 工程从 `code_start`
冷启动（或被调试器直接加载到 `main`）都必须按此序：

| 步 | 动作 | 为什么 |
|---|---|---|
| 0 | `board_ramfunc_relocate()` + `board_ramfunc_ready()` 校验 | driverlib 的 `SysCtl_delay()` 编入 `.TI.ramfunc`（见下）；不先拷贝 = 跳进空 RAM |
| 0b | `SysCtl_disableWatchdog()` | 复位后看门狗默认使能；调试器加载可能绕过 `code_start/wd_disable` 直达 `main` |
| 0c | `Interrupt_initModule()` + `Interrupt_initVectorTable()` | PIE 禁用时任何陷阱的向量取自 boot ROM，其 ITRAP handler 会**使能看门狗并等复位** |
| 1 | 时钟（PLL 120MHz + LSPCLK/4 + 回读校验） | 120MHz 不符即 fail-safe |
| 2 | GPIO/SCI 等外设初始化 | — |

### `.TI.ramfunc` 重定位（2026-10-17 破案：启动即挂死的根因）

driverlib 的 `SysCtl_delay()` 以**内联汇编**编入 `.TI.ramfunc` 段——它在时钟树 /
Flash 等待态重配期间被调用，必须身在 RAM。flash 链接脚本因此把该段拆成两半：

    .TI.ramfunc : LOAD = FLASH_BANK0_SEC1, RUN = RAMLS0 (= 0x8000), ...

C 运行库 `_c_int00` 只清零 `.bss`、展开 `.cinit`，**不做 LOAD→RUN 的段拷贝**。
缺少显式 memcpy 时，`SysCtl_setClock()` 首次调用 `SysCtl_delay()` 即跳进空
RAMLS0，把 `0x0000` 当指令执行 → 非法指令陷阱（ITRAP）。此刻 PIE 未初始化，
陷阱向量从 boot ROM 取，`CPU1BROM_itrapISR` 使能看门狗等复位——表现为
**"启动几毫秒即死：无串口输出、无 LED 活动、HIL 全挂"**。

- 破案证据（diag10/diag11）：ITRAP 现场故障 PC = `0x3FEEF8`（ROM 向量区）；
  停机 PC 反复停在 `board_clock_init`（0x82A3A）；RESC=0（非真实复位事件）。
- 修复（已进参考工程）：`main.c` 入口 memcpy 拷贝 + `board_ramfunc_ready()`
  逐字校验（防链接脚本改动丢失 `Ramfuncs*` 符号或烧了旧镜像）；
  `board_clock_init()` 内防御性再拷一次，任何调用方都不可能踩雷。
- 判读口诀：**"启动即死、PC 停在时钟初始化" → 先查 `.TI.ramfunc` 重定位**。

## SCI 日志观测（默认日志通道）

- SCIA TX=GPIO29 → XDS110 虚拟 COM：串口工具打开对应 COM 口，**115200 8N1**。
- LSPCLK 固定 30MHz（`SysCtl_setLowSpeedClock(SYSCTL_LSPCLK_PRESCALE_4)`），
  波特率 BRR 按 115200 计算（误差 ≈1.4%，在 SCI 容差内）。
- 无接收端时写入会阻塞？——本实现为**轮询发送**，不依赖对端握手，主机未打开串口也不影响 CPU 运行。
- **捕获窗口**（run-hil.ps1）：dss.bat 的 JVM 启动 + 连接 + 烧录要 20-60s，固件才会首次启动；
  H6 收尾还会从 `code_start` 重新引导并**再打一次 banner**。`-SerialSeconds` 必须覆盖整段
  DSS 运行（默认 90s）。窗口 20s 时日志为空——那是窗口问题，不是固件没输出。

## DSS / HIL 调试经验（2026-10-17 实证）

- **`readWord` 只读 16 位**：H5 曾用 `readWord(0, 0x7F00)` 判断 LED 亮灭，而 GPIO20/22 在
  32 位 GPADAT 的**高字 0x7F01**，永远读不到 → `led4On=led5On=true` 恒真 → 假 FAIL。
  修复：高/低两个字都读再拼接（`(hi<<16)|lo`），或读 GPADAT_R@0x7F80。见 `hil_test.js`。
- **未用引脚会"闹鬼"**：GPIO0-13 等未配置引脚上拉默认关闭（GPAPUD 全 1），悬空输入电平不定——
  GPADAT 低字观测到随流水灯节拍翻转的噪声值（0x3FFF/0x0/0x812…），GPBDAT 低字随 JTAG
  （GPIO35-38）扫描活动变化。二者均**非固件写入**（`GPIO_writePin` 断点差分证实固件只动
  0x7F02/0x7F04；GPADAT_R 读回稳定）。判读 LED 只能看高字 0x7F01 或 GPADAT_R 0x7F80。
- **GEL_MapOff()**：ccxml 的 GEL 内存映射把调试器访问限制在 RAM/flash，外设帧（GPIO/CPUSYS/PIE/
  CPU timer）读会报 0x20000；`expression.evaluate("GEL_MapOff()")` 之后放可访问整个 C28x 空间。
- **AutoRunToLabelOnRestart=false**：否则 loadProgram 后 CCS 自动跑到 main，跳过
  code_start/wd_disable，看门狗 WDRST 死循环（无日志无灯）。
- **符号断点可能回退到 AET**：`breakpoint.add("GPIO_writePin")` 偶发
  `Error -1066 ... Retrying with a AET breakpoint`——AET（ERAD）断点功能等价，可忽略。
- **`PC = code_start` + `runAsynch` + `disconnect`**：这是本板唯一可由探针触发的"等价冷启动"（H6）。
  机理（2026-10-17 定案）：F28003x 没有 `-TRST` 引脚，boot ROM 用 **RESC bit31 DCON** 判断仿真器是否在线，
  在线即走 **Emulation Boot**；仿真引导键（OTP 里的 0x5A 键）无效 → 落入 Wait/SCI 引导。
  实测：`target.reset()` 后 PC 停在 `0x3FB8B9`（boot ROM SCI wait）超过 5s 不交接，
  halt-free LED 翻转数 = 0（diag17/diag20），同一 flash 镜像强设 `PC=0x80000` 立刻正常启动。
  **推论**：接探针时"复位后自动跑 flash"永远不会发生，这不是固件缺陷；而**离线（拔探针/断电重上电）
  走 Stand-Alone Boot 会引导 flash——这条路径无法用探针自动验证，只能人工断电重启**（见"未覆盖项"，ADR 0006）。
- **诊断脚本**：`tools/dss/diag*.js` 为历次排查工具；`diag15.js` 是"断点差分法"标杆——
  在 `GPIO_writePin` 入口下符号断点，每次命中快照 GPIO 数据块并 diff 相邻快照，
  直接定位驱动实际改写的字；同时可验证 flash 常量表与 ACC（pin 实参）。
- **流水灯节拍与时钟**：H5 在**核心保持运行**的状态下以 ~20ms 间隔 peek GPADAT_R 双字，
  用"首尾跳变跨度/(跳变数-1)"求平均步进周期——量化误差被平均掉，该周期同时证明 SYSCLK=120MHz
  （步进 = 200 个 CPUTimer0 tick，tick = PRD/SYSCLK，PRD 由固件按 120MHz/1kHz 算出）。
  实测均值：2026-10-18 四轮各 12 次跳变 **197.0 / 195.8 / 196.5 / 195.0ms**（当前证据 `harness/tests/on-target/records/hil-2026-10-18-led-chaser.md`）；
  2026-10-17 四轮独立实测 192.5 / 193.5 / 194.5 / 195.1ms（各 12 次跳变）。
  跨两日八轮合计散布 192.5–197.0ms（跨 2.3 %），说明 HIL 容差只能定在 ±25 %：门禁判据（`CADENCE_TOL=0.25`）与
  方法可复现性由此同时成立，±2 % 属仪器量级、本路径不可裁决（见"未覆盖项"与 ADR 0009）。
  **切勿**改成"halt—读—run"循环测节拍：halt 期间的多个 TIF 溢出只会算一次，实测把 200ms 拉成 426ms。
- **读内存前必须确认已 halt**：`target.halt()` 是异步的，核心还在跑时读外设**同样**报
  0x20000。`hil_test.js` 的 `haltAndWait()` 轮询 `isHalted()` 直到确认为止——
  这是 0x20000 的第二个成因（第一个是 GEL 映射，见上）。
- **H3 不能单独判读（假阳性）**：`g_self_test_code` 静态初值即 0，"自检真过"与
  "main 从未走到 `self_test_run()`"读数相同。必须与 H5 节拍采样（证明主循环在跑）
  及 SCI banner 组合判读；`hil_test.js` 因此把 H3 的读取放在采样窗口**之后**。
- **loadProgram 带不带 argv 是两条路**：DSS `memory.loadProgram(file)`（HIL 用）
  不需要 `__c_args__`；loadti 内部调 `memory.loadProgram(file, argvArgs)`
  （argv[0]=.out 路径），**要求镜像定义 `__c_args__`**，否则
  `SEVERE: __c_args__ not defined ... Error code #4011`。修复 = 链接加
  `--args=0x200`（Makefile 已含；自检：map 里 `__c_args__ = abs ffffffff`
  即未定义）。详见 ADR 0004。
- **会话选项有时序**：`AutoRunToLabelOnRestart=false` 与 `GEL_MapOff()` 必须在
  `loadProgram` **之前**设置——load 之后 CCS 已按默认选项自动运行并建好 GEL 映射，
  再改就晚了。
- **改 Makefile/LDFLAGS 后行为没变？** `.out` 目标若不依赖 Makefile 就不触发重链
  （参考工程已把 `Makefile` 加进 `.out` 依赖）；必要时 `ccs.ps1 rebuild`。

## 时钟（重要，见 ADR 0001）

- 默认 **INTOSC2 10MHz → PLL → 120MHz**（不依赖外部晶振，对开发板改版鲁棒）。
- `board_clock.c` 里 `ASSERT(SysCtl_getClock(10000000U) == 120000000U)`；
  Release 构建下用返回值判断，失败即进入 fail-safe 形态（双灯快闪）。

| 现象 | 处理 |
|---|---|
| `Error -2131 @ 0x0`（IcePick 层） | 用了标准 JTAG ccxml → 换 LaunchPad ccxml；或 TCLK 降到 5.5MHz |
| `Error -260 @ 0x0`（IcePick 初始化失败，`ccs.ps1 probe` 也 Found 0 devices） | XDS110 掉线：查 USB 线/口、板子供电；先 `probe` 确认设备在枚举中再跑 HIL |
| 探针找不到 | 换 USB 口/线；`ccs.ps1 probe` 查；确认 Shunts 正常供电 |
| 烧录后无日志 | 先看 `-SerialSeconds` 是否覆盖整个 DSS 运行（默认 90s）；再确认 COM 口号与 115200；确认 `board_clock` 未走 fail-safe |
| SCI 日志为空但 H1-H6 全 PASS | 串口窗口太短（banner 出现在 DSS 启动后 20-60s）或 COM 口选错；拉长窗口重跑 |
| GPADAT 低字翻转/花值 | 未用引脚悬空噪声（上拉默认关），非固件问题；看高字 0x7F01 / GPADAT_R 0x7F80 |
| H5 报 `led4On=led5On=true` | 用了 16 位读 0x7F00——LED 位在高字 0x7F01；`hil_test.js` 已修复为双字拼接 |
| `.text` 超 banks | `ccs.ps1 size`；提高优化等级（`--opt_level`）或裁剪日志字符串 |
| JTAG 永久失连 | 检查是否误把 GPIO35–38 配成 GPIO；需按 TI 官方恢复流程处理 |
| `SEVERE: __c_args__ not defined`（loadti，错误码 4011，load failed） | 链接缺 `--args=<n>`：Makefile LDFLAGS 已加 `--args=0x200`（2026-10-17 修复）；仅影响 loadti（`ccs.ps1 program`），HIL 的 `loadProgram(file)` 不带 argv 不受影响；map 中 `__c_args__ = abs ffffffff` 即未定义 |
| `GEL: Encountered a problem loading file ... Could not open file` | `.out` 不存在或 0 字节（未构建/构建失败）：先 `ccs.ps1 build`，再确认路径与配置（CPU1_FLASH/CPU1_RAM） |
| 启动几毫秒即死：无串口、无 LED、PC 停 `board_clock_init` | `.TI.ramfunc` 未重定位 → ITRAP → 看门狗复位，见"固件启动顺序"节；diag10/11 可现场抓 ITRAP |
| 改了 Makefile/LDFLAGS 但现象不变 | `.out` 未重链（目标不依赖 Makefile；已修）；`ccs.ps1 rebuild` 强制全量重建 |
| 串口一字节不出，但 H1-H4/H6 全通过、`CTL1=0x0000`、`LBAUD=0x0000` | SCIA 外设时钟未使能：`board_clock_init()` 需 `SysCtl_enablePeripheral(SYSCTL_PERIPH_CLK_SCIA)`（PCLKCR7@0x5D330 bit0）；HIL 的 `H3-sciclk` 直接抓这个，见 ADR 0005 |
| 节拍实测值随采样方式漂移（同一次运行 50ms/124ms/426ms 都出现过） | 别信 halt 采样：TIF 单标志会把 halt 期间的溢出压成一次；另外 PRD 若按 SYSCLK/4 误算会让固件真的快 4 倍。用 halt-free peek + `period = SYSCLK/tick_hz`（ADR 0005） |
| `gmake: *** [Makefile:72: dirs] Error 1` + `/usr/bin/sh: syntax error: unexpected end of file` | gmake 取了 Git Bash 的 `sh.exe` 解释 Windows 配方；`ccs.ps1` 现固定传 `SHELL=cmd`（2026-10-17 修） |
| `[FAIL] No Makefile in E:\repo\E:\...\projects\...` | `-Project` 传了绝对路径被 `Join-Path` 拼接；`Get-ProjDir` 已支持绝对路径（2026-10-17 修） |
| `ccs.ps1` 从非 PowerShell 父进程启动就乱码/找不到命令 | 调用侧 PATH 需含 `C:\Windows\System32;C:\Windows`；这是**调用环境问题**，不是工具缺陷（构建配方已用 `SHELL=cmd` 兜底） |
| `ConvertFrom-Json` 报「未终止的字符串」但文件用编辑器看着完全正常 | PowerShell 5.1 的 `Get-Content` 默认按本地 ANSI(GBK) 解码**无 BOM 的 UTF-8** JSON，中文被拆坏后连带吃掉引号。真相源（spec/trace/state/targets）一律 `-Encoding UTF8` 读、`-Encoding UTF8` 写（`spec.ps1:50/67/106`、`run-hil.ps1:230`）；手写 ad-hoc 校验命令也必须带 `-Encoding UTF8`，否则会误报"JSON 坏了" |
