## 10. 魔鬼代言人（对本审计结论的反例）

| # | 反例 | 触发条件 | 影响 | 缓解 / 接受理由 |
|---|---|---|---|---|
| 1 | 「9 腿全绿 = 工程完备」是本报告自己可能犯的错 | 门禁只覆盖**已存在**的工程与 spec；`full-platform` 不存在 → 没有人给它跑门禁 | 绿的是"局部"，被读成"整体完备" | §0 已把命题拆成两半并分别判定；§6 用覆盖矩阵显式列出 16 类缺口，避免以偏概全 |
| 2 | 新建 `.gitignore` + `git rm --cached` 可能误伤证据 | 若过滤正则过宽，会把 `records/*.md` 或 `state.json` 一起移出索引 | 证据链断裂，trace 引用失效 | 过滤后复核：剩余被跟踪产物 **0**；`records/*.md`、`state.json`、`build-verify/*.log` 均在保留清单内且未被动 |
| 3 | CI workflow 建了但从未在 CI 上跑过，"有 CI"是假的 | workflow 未推送 / 无 self-hosted runner / `RUN_FW_BUILD` 未开 | 交付一个"看起来有 CI"的空壳，违反 ADR 0009「绿但不会红」 | workflow 头注释 + §7 显式声明"未推送不生效"、`firmware-build` 默认不跑；在推送并首跑前，本项不得被记为"通过" |
| 4 | 补的 `trace.tests` 指向脚本文件而非用例，追溯仍可能是纸面的 | `hil_test_mp.js` / `run-hil.ps1` 是判据**实现**，不等于"该 REQ 有独立用例" | 需求→测试映射形式化但语义弱 | 硬件相关 REQ 主机侧无纯逻辑单测是客观事实；已选择"指向真实判据脚本"而非编造不存在的用例，并在 trace 注释里写明原因 |
