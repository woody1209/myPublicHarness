# 20 · AI 生产规范（展开）

AGENTS.md 是精简强制版；本文件解释**为什么**与**怎么做**。
（与 `C3M3-harness` 同源：确定性 Facility + agent 生成 + 脚本收口。）

## 1. 确定性原则

AI 产出固件最大的风险是"看起来对"——对本仓库，任何结论必须可复现：

1. **命令统一入口**：`harness/tools/ccs.ps1`（构建/尺寸/烧录）与
   `harness/tools/run-host-tests.ps1`（逻辑回归）。它固定了 CCS 根目录、编译器
   目录、C2000Ware 目录、gmake 路径与 `--flash/-ram` 配置。散落调用 `cl2000`
   是评审拒绝项。
2. **版本锁定**：以 `harness/env/manifest.json` 记录的 CCS / C2000Ware / 编译器
   版本为准；升级必须重跑 `doctor.ps1` 并在 ADR 或 docs/10 记录。
3. **构建产物**：每次改动的验证 = `ccs.ps1 build` + `run-host-tests` + `ccs.ps1 size` 三项留痕。

## 2. 变更分级与流程

| 级别 | 例子 | 要求 |
|---|---|---|
| S | 源文件逻辑（`source/*.c`） | build + host tests + README/docs 更新；**新模块/新行为需先写 spec** |
| M | 时钟策略 / 引脚分配 / 链接脚本 / **启动顺序（ramfunc 重定位、看门狗、PIE）** / 外设初始化 | regen-equivalent（手工同步 `board_pins.h` 与 target card）+ build + ADR/docs 记录；**需先写 spec** |
| L | 工具链 / C2000Ware 升级、RTOS 引入 | ADR + 双配置构建（CPU1_FLASH / CPU1_RAM）+ 回归；**需先写 spec** |

spec 的判定口径与流程见 `specs/README.md` 与 `70-Spec驱动开发.md`：
**改动会引入新的对外行为或新的硬件依赖 → 先写 spec 再写代码。**

## 3. 分层铁律

```
source/<module>.c          纯逻辑：只依赖 C 标准库 → 主机可测
source/<module>_hw.c       硬件相关：driverlib / 寄存器 → 只进 target 构建
source/board_*.c           系统级：时钟、看门狗、引脚分配
device/                    器件相关源（codestart 等，随器件)
```

主机测试层（`harness/tests/host`）**只允许**包含纯逻辑模块；硬件代码不可达。

## 4. 日志与可观测性

- 统一 `sci_log` → SCIA → XDS110 虚拟 COM：115200-8N1，不占额外引脚
  （TX=GPIO29 / RX=GPIO28 是官方 LaunchPad 映射）。
- 关键路径（启动、自检、异常）必须打日志；日志由 `fmt`（纯逻辑格式化〉+ `sci_log`（硬件）组成。
- **禁止 `sprintf` 到定长缓冲**：格式化走 `fmt`（带长度边界、返回写入字节数，可被主机侧单测覆盖），
  再由 `sci_log`（硬件层）发送。

## 5. 提交与留痕

- 提交信息必须包含：改了哪些工程、构建结果（`.text` 增量）、测试结果。
- 环境类发现（工具路径/版本/坑）写 `harness/docs/10-环境总览.md`「环境修复备忘（踩坑记录）」。
- 目标芯片或板级事实变化 → 更新 `targets/F280039C.json` 并在提交信息注明来源。

## 6. 安全红线汇总

- 不擦片（`erase` 必须显式 `-Confirm` 且用户确认）；不烧错工程（一次一个 `-Project`）。
- 不得复用 GPIO35–38；不得改 XDS110 的 cJTAG 连接配置而不在 docs/40 记录。
- **启动顺序红线**（ADR 0003）：`main()` 首动作必须 `.TI.ramfunc` 重定位 + ready 校验，
  其后才允许 `SysCtl_*`/延时；随后禁看门狗 → PIE → 时钟 → 外设。
  违反的后果是"启动几毫秒即死"（ITRAP → boot ROM 看门狗复位，无日志无灯）——
  2026-10-17 实证根因，判读口诀见 docs/40"固件启动顺序"节。
- **链接红线**（ADR 0004）：Makefile LDFLAGS 必须保留 `--args=<n>`（定义 `__c_args__`）；
  删除会导致 `ccs.ps1 program`（loadti）报 4011——HIL 路径不报，属"静默 half-broken"。
- 生产件注意 DCSM：Zone1/Zone2 的密码与锁定一旦写入不可逆；上电/调试前先以只读方式确认目标状态。

## 7. 规格先行与三段式执行模型

本仓库把"确定性"推广到**工作流**本身：**确定性的东西用脚本，生成性的东西交 Agent，
脚本负责收口**（rule → agent → rule）。

| 轨 | 承担者 | 本仓库实例 |
|---|---|---|
| rule（确定性） | 本地脚本 | `doctor.ps1` 环境探测、`ccs.ps1` 构建/尺寸/烧录、`run-host-tests.ps1` 回归、`spec.ps1 check` 校验 |
| agent（生成性） | Agent / 人 | spec 三件套正文、固件 C 代码、ADR 决策说明 |
| rule（收口） | 本地脚本 | `spec.ps1 check` 通过 = 规格侧完成；DoD 清单 = 交付侧完成 |

**规格先行**：非平凡改动先在 `specs/<id>/` 写 `requirements.md`（EARS 验收）→
`design.md`（需求覆盖表）→ `tasks.md`（可勾选任务），**逐阶段经用户确认**后再实现。
每一步都要**可判定**：EARS 句可观测、验收有命令、任务有勾选、REQ 有追溯。

运行时状态快照写入 `projects/<proj>/state.json`（契约 `harness/schemas/state.schema.json`）：
各工具只读写自己负责的顶层字段，只记指针与统计——**真相是产物与命令输出，state 只是快照**。
